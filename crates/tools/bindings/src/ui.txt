// The framework's own Windows surface: reading pointer input, recognising gestures,
// the rotary controller, the touch keyboard, text services and UI Automation.
//
// Creating the window and opting it into pointer input belong to `windows-window`;
// this crate reads what those opt-ins deliver. Both crates name `HWND`, which is a
// raw-pointer alias in this style and so is one type across both.
//
// `default` is the metadata bundled with windows-bindgen; the second input carries
// the UI Automation provider API and its identifiers, which that corpus lacks. See
// `metadata/uiautomation.rdl`.
--in default target/authored.winmd

// ── Gesture recognition ───────────────────────────────────────────────────────
// The system recogniser, fed the same pointer points the hit test resolved, so a
// gesture and a hit agree by construction. `PhysicalGestureRecognizer` is the
// precision-touchpad path, which reports in physical units rather than as a
// synthesized wheel.
//
// Members are named individually because `--minimal` generates a class named alone as a
// shell with nothing callable on it — the same trap `windows-window` hit on
// `IDisplayInformation5`. What is *not* named is as deliberate: no `CanBeDoubleTap` (the
// recogniser answers double-tap itself through `GestureSettings::DoubleTap`), no
// `MouseWheelParameters` (wheel over a scroll surface is the tracker's, and wheel over
// anything else is a gesture whose step this stack states), and no cross-slide thresholds
// (there is no cross-slide consumer yet, and a threshold set from nowhere is worse than the
// default).
    Windows.UI.Input.GestureRecognizer
